- `src/app/[locale]/proposals/[id]/page.tsx` — proposal detail
- `src/app/[locale]/proposals/page.tsx` — proposals list
- `src/app/[locale]/applications/page.tsx` — applications list
- `src/app/[locale]/contributions/page.tsx` — contributions list

**Pages that DO use shared states.tsx** (for reference, 11 pages): ApplicationsClient, reset-password/[token], reset-password, signin, signup, opportunity detail actions, application decision client, opportunity edit, opportunity new, proposal actions, proposals/new.

**Current state**: no broken UX. All pages either render content or render a graceful empty/redirect state. Gap is consistency, not a defect.

**Why deferred**: per-page state wiring is a UX polish task that doesn't affect functionality. The shared `states.tsx` components exist and work; the task is to replace inline `if (loading) return <div>Loading...</div>` patterns with `<LoadingState />` imports.

**Applicability principle (per ChatGPT directive)**: NOT every page needs all three states. The acceptance bar is "applicable states per page, not formal padding". Specifically:
- **Static pages** (e.g. `src/app/[locale]/page.tsx` — home, server-component with static content): no LoadingState needed (no async data fetch). May need ErrorState for unexpected server errors. EmptyState is N/A.
- **List pages** (e.g. `proposals/page.tsx`, `organizations/page.tsx`, `talent/page.tsx`): need all three — LoadingState during fetch, EmptyState when no records, ErrorState on fetch failure.
- **Detail pages** (e.g. `proposals/[id]/page.tsx`, `organizations/[id]/page.tsx`): need LoadingState + ErrorState. EmptyState is N/A (a non-existent detail should 404, not show "empty").
- **Action pages** (e.g. `proposals/new/page.tsx`, `opportunities/new/page.tsx`): typically no LoadingState (form is interactive). May need ErrorState on submit failure. EmptyState is N/A.
- **Authenticated dashboard pages** (e.g. `dashboard/page.tsx`, `admin/page.tsx`): need all three — LoadingState during data fetch, EmptyState when no items, ErrorState on failure.

**Acceptance bar**: for each of the 21 pages, document which of the three states are actually applicable (per the matrix above), then wire ONLY those applicable states from `@/components/shared/states`. Per-page E2E test verifies each APPLICABLE state renders correctly. Pages must NOT add formal/unused states just to "tick a box".

**Owner**: GLM (G09 or dedicated UX-polish round).

**Estimated effort**: ~4 hours (template per page: ~12 minutes including import swap + E2E verification).

### D5. g03-proposal-flow.spec.ts:204 flaky test

**Scope**: `tests/e2e/g03-proposal-flow.spec.ts:204` — "G03 — Full Institutional Governance E2E › propose → review → revise → approve → team → invite → reject"

**Current state**: passes on retry. CI #171, #172, #173, #175, #176 all green. The test has Playwright's default retry behavior (max 2 retries) and the second attempt always succeeds.

**Root cause**: `const PROPOSER_EMAIL = \`${PREFIX}-proposer@str-test.local\`;` is declared at module load time. Both the "Minimal step-by-step" describe block (line 144, test calls signupAndVerify at line 151) AND the "Full Institutional Governance E2E" describe block (line 203, test calls signupAndVerify at line 210) use the SAME email. The second test's signup encounters an email collision (the first test already created the user), and the email verification flow handles this inconsistently — sometimes the verify URL is invalid (already consumed), causing the "verified successfully" text to not render.

**Why deferred**: fix requires generating a unique email per test (e.g., `const PROPOSER_EMAIL = \`${PREFIX}-proposer-${Math.random()}@str-test.local\`;` evaluated inside each test, not at module load). Out of scope for G08 defect-correction.

**Acceptance bar**: refactor `PROPOSER_EMAIL` and `INVITEE_EMAIL` to be generated per-test. Verify the test passes consistently without retry across 5 CI runs.

**Owner**: GLM (G09 audit or G03 follow-up).

**Estimated effort**: 30 minutes.
