# NEXUS Restaurant — GLM BUILD MISSION

## Mission Identity

You are the principal implementation engineer responsible for building the **NEXUS Restaurant Domain** as a real application on top of the independent **NEXUS-AO** architecture.

The mission is governed by two normative documents:

1. `NEXUS_Agentic_Operations_Architecture_Specification.md`
2. `NEXUS_Restaurant_Domain_Specification.md`

The first defines the universal architecture.
The second defines the restaurant domain implementation.

Your responsibility is to implement the second document **as a consumer of the first**.

You are not being asked to redesign NEXUS-AO.

You are not being asked to copy NEXUS-AO into the restaurant repository.

You are not being asked to build a generic multi-agent demo.

You are being asked to build a production-oriented restaurant operating application that uses the upstream NEXUS-AO implementation as its reusable operational foundation.

# 2. MANDATORY UPSTREAM CONSUMPTION MODEL

NEXUS-AO MUST be consumed as an external reusable dependency.

Do not copy the NEXUS-AO source tree into the Restaurant project.

Do not create a private fork inside the Restaurant repository.

Do not duplicate NEXUS-AO classes, services, schemas, event contracts, or infrastructure merely to avoid importing the upstream package.

The Restaurant project must depend on a **specific reproducible NEXUS-AO release**.

Preferred order of dependency identity:

1. immutable tagged release;
2. immutable commit SHA;
3. another reproducible immutable artifact explicitly defined by NEXUS-AO.

Do not depend on an unpinned moving branch for production behavior.

The exact upstream NEXUS-AO version or commit MUST be recorded in the Restaurant repository.

# 7. NON-NEGOTIABLE DOMAIN PRINCIPLES

The implementation MUST preserve the following principles:

- agent output is not operational truth;
- customer intent is not automatically a commitment;
- availability must be verified before commitment;
- resource constraints must be enforced deterministically;
- no silent substitution of requested products or modifiers;
- customer consent is required for material alternatives or changes where specified;
- one table can contain multiple independent guest orders and preferences;
- customer memory must not override current explicit customer intent;
- sensitive preferences require appropriate consent and handling;
- payment state is authoritative outside the LLM;
- inventory state is authoritative outside the LLM;
- reservation state is authoritative outside the LLM;
- order state is authoritative outside the LLM;
- kitchen/production state is authoritative outside the LLM.

---

# 8. NO ARTIFICIAL AGENT EXPANSION

Do not create an agent for every noun or CRUD operation.

Use deterministic services for deterministic operational functions.

Use agents where reasoning, natural-language interaction, coordination, interpretation, negotiation, or adaptive orchestration provides actual value.

The specialist agent roster defined in the Restaurant Domain Specification is the baseline.

Do not invent additional permanent agents merely because the framework makes them easy to create.

Dynamic or temporary sub-agents may be used only where the specification defines a measured capability/workload justification.

---

# 9. SWARM ENGINE INTEGRATION

Swarm Engine is the orchestration foundation.

Do not replace it with another orchestration framework.

Integrate with the actual upstream NEXUS-AO and existing Swarm Engine interfaces discovered during Phase 0.

The Restaurant project must not move authoritative operational state into the orchestration layer.

Maintain the conceptual boundary:

```text
Restaurant UI / Channels
        ↓
Restaurant Agent Layer
        ↓
Swarm Engine / NEXUS-AO orchestration capabilities
        ↓
Restaurant Domain Services
        ↓
PostgreSQL / Operational Truth
        ↓
External Integrations
```

The exact implementation may differ according to the public NEXUS-AO contract, but the responsibility boundaries must remain intact.

---

# 10. DATABASE AND TRANSACTIONAL TRUTH

PostgreSQL remains the authoritative transactional source of truth as required by NEXUS-AO and the Restaurant Domain Specification.

Enforce important invariants using:

- database constraints;
- transactions;
- proper locking/concurrency control;
- unique constraints;
- idempotency;
- versioning where required;
- deterministic domain services.

Never ask an LLM to decide whether a reservation, inventory allocation, payment transition, or table commitment is safe.

The LLM can request an action.

The domain/application layer decides whether the action is legal and operationally valid.

# 14. CUSTOMER EXPERIENCE MODEL

The Master Waiter is the primary customer-facing interaction agent.

It must support natural-language and structured interaction where defined.

Examples include:

- menu discovery;
- category exploration;
- modifier selection;
- preference capture;
- table ordering;
- reservation;
- pre-order;
- order modification;
- clarification;
- availability explanation;
- billing interaction;
- customer preference recall.

The Master Waiter MUST NOT promise unavailable actions before downstream validation.

Example:

Customer asks for an unavailable ingredient.

Correct behavior:

```text
Master Waiter
    ↓
Food Agent / Domain Service
    ↓
Availability Check
    ↓
Unavailable
    ↓
Approved alternatives or removal
    ↓
Customer consent
    ↓
Commit
```

Never silently substitute.

---

# 15. MULTI-GUEST TABLE MODEL

A table is not a single customer order.

The implementation must support:

```text
Table
 ├── Guest A
 │    ├── Order lines
 │    └── Preferences
 ├── Guest B
 │    ├── Order lines
 │    └── Preferences
 └── Guest C
      ├── Order lines
      └── Preferences
```

Guest-specific preferences must remain associated with the correct guest/order line.

The final bill may aggregate items while preserving per-guest attribution where required.

---

# 16. CUSTOMER MEMORY

Customer memory is a domain capability, not a conversational trick.

The implementation must distinguish:

- current explicit request;
- learned preference;
- preference confidence;
- sensitive preference;
- historical preference;
- temporary context.

Current explicit customer intent must take precedence over remembered preferences.

One isolated complaint or observation must not automatically rewrite a persistent preference unless the domain rules explicitly justify it.

Provide appropriate customer control for stored preferences as specified.

---

# 17. FEEDBACK AND CONTINUOUS IMPROVEMENT

Feedback must be connected to actual operational data through deterministic identifiers and timestamps where appropriate.

The Feedback Agent must remain non-intrusive.

The Operations Agent may identify:

- recurring delays;
- repeated negotiation failures;
- workload spikes;
- repeated availability failures;
- customer dissatisfaction patterns;
- operational bottlenecks.

The Operations Agent may recommend or instantiate additional capabilities only according to the measured conditions and policies defined by the Restaurant Domain Specification.

Do not spawn agents merely because more agents are technically possible.

---

# 18. KITCHEN / PRODUCTION MODEL

The application must maintain the distinction between:

- customer order state;
- production task state;
- staff execution;
- delivery/hand-off confirmation.

An agent saying “ready” is not sufficient proof of physical completion.

Where human confirmation is required, the application must model that explicit confirmation.

Kitchen/KDS integration must be based on durable state and idempotent task handling.

---

# 19. PAYMENT AND BILLING SAFETY

Payment operations are high-risk operations.

Never allow free-form model output to directly mutate financial state.

Payment actions must go through:

- authorization;
- deterministic validation;
- provider SDK/API integration;
- idempotency;
- audit;
- explicit status transitions.

Never store raw card credentials in application state unless a fully compliant provider mechanism explicitly requires it; prefer provider-hosted/tokenized payment flows.

Do not invent PCI-sensitive infrastructure.

---

# 20. INVENTORY SAFETY

Inventory must be authoritative and transactional.

Support at minimum where specified:

- availability checks;
- reservations/holds where needed;
- deductions/consumption;
- replenishment-related state;
- concurrency safety;
- shortage handling;
- auditable mutations.

Do not allow an LLM to decrement inventory directly.

---

# 21. RESERVATION SAFETY

Reservation handling must prevent:

- double booking;
- invalid table assignment;
- overlapping reservations where prohibited;
- commitment without resource availability;
- inconsistent state after retries.

Use transactional mechanisms defined by NEXUS-AO.

Concurrency tests are mandatory for reservation contention.

---

# 22. EXTERNAL INTEGRATIONS

Possible categories include:

- POS;
- KDS/KOT;
- payment provider;
- messaging;
- delivery channels;
- printers/hardware;
- identity/authentication;

      ↓
Vendor Adapter
      ↓
External System

# 23. MCP TOOL BOUNDARIES

Every restaurant tool exposed to agents must have:

- clear schema;
- validation;
- authorization;
- auditability;
- idempotency where mutation occurs;
- error handling;
- deterministic domain invocation.

MCP is an interface boundary, not a permission bypass.

Never expose direct database write access to an LLM tool.

Never expose an unrestricted “execute arbitrary SQL” tool to restaurant agents.

# 28. MANDATORY CONCURRENCY SCENARIOS

At minimum, test scenarios equivalent to:

### Scenario A — Two customers reserve the same table concurrently

Expected:

- at most one valid commitment;
- deterministic conflict handling;
- no duplicate reservation state.

### Scenario B — Two orders consume the last available stock

Expected:

- inventory cannot become falsely available through a race;
- one or more requests are rejected/adjusted according to policy;
- no negative inventory unless explicitly permitted by domain policy.

### Scenario C — Payment retry

Expected:

- duplicate client retry does not create duplicate financial effect.

### Scenario D — Duplicate event

Expected:

- idempotent event processing where required;
- no duplicate operational effect.

### Scenario E — Agent/tool timeout after commit

Expected:

- final state remains coherent;
- recovery does not duplicate the committed operation.
