# مقدمة الدردشة إلى GLM — Voxa Studio

أنت الآن المسؤول الرئيسي عن تنفيذ مشروع **Voxa Studio — Knowledge, Narrative & Voice Studio**.

أرفقت لك ملفين، ويجب التعامل معهما معًا باعتبارهما **حزمة التنفيذ الرسمية والملزمة للمشروع**:

1. `VOXA_Studio_Architecture_Specification.md`
2. `VOXA_Studio_GLM_BUILD_MISSION.md`

المطلوب منك ليس تحليل الفكرة أو اقتراح معمارية جديدة، بل **بناء Voxa Studio فعليًا من البداية إلى النسخة القابلة للاستخدام والاختبار وفق الوثيقتين**.

اعتبر وثيقة `VOXA_Studio_Architecture_Specification.md` المرجع الهندسي الأعلى الذي يحدد ماهية النظام، حدوده، مكوناته، عقوده، البيانات، الـpipelines، الـinvariants، مراحل البناء ومعايير القبول.

واعتبر `VOXA_Studio_GLM_BUILD_MISSION.md` بروتوكول التنفيذ الذي يحدد كيف تدير البناء، الاختبارات، الـcheckpoints، Git، معالجة الأخطاء، الاستقلالية المسموحة لك، وما الذي يمنع عليك تغييره.

اقرأ **الملفين كاملين** قبل أي تنفيذ جوهري. لا تعتمد على قراءة العناوين أو الملخصات فقط.

هذا المشروع متعمد أن يكون **Local-first، compact، وقابلًا للتوسع عبر Adapters دون تضخم معماري**. لا تحوله إلى Microservices، ولا تضف Swarm أو A2A أو Redis/Celery أو Message Broker أو Vector Database أو بنية موزعة ما لم تتغير الوثيقة رسميًا. نحن نريد تطبيقًا قويًا، لا معرضًا للأنماط المعمارية.

أنت مفوض باتخاذ قرارات التنفيذ الداخلية الطبيعية التي لم تُحسم نصيًا، بشرط أن تختار **أبسط حل تقليدي يحقق المتطلبات ويحافظ على الـinvariants**. لا تسألني عن قرار حسمته الوثائق، ولا توقف العمل بسبب تفاصيل يمكن لمهندس رئيسي حلها بنفسه.

في المقابل، لا تملك صلاحية إعادة تصميم المنتج أو استبدال قراراته الأساسية بصمت. إذا اكتشفت تناقضًا حقيقيًا أو عيبًا معماريًا، حدده بدقة، اذكر القواعد المتعارضة، أوقف الجزء المتأثر فقط، واقترح أصغر تصحيح ممكن بدل التخمين.

المطلوب أن تدير دورة التنفيذ كاملة بنفسك:

**Read → Inspect → Implement → Test → Verify → Simplify → Checkpoint → Commit → Continue**

لا تعتبر وجود الكود إنجازًا كافيًا. كل Phase يجب أن تجتاز بوابة القبول الخاصة بها واختباراتها قبل الانتقال إلى التالية.

أريد تنفيذًا هندسيًا حقيقيًا وليس Prototype أو Demo سريعًا.

هناك شرط صارم إضافي لهذا المشروع: **مقاومة تضخم الملفات والتعقيد**. لا تنشئ مجلدات وطبقات وFactories وManagers وServices لمجرد التنظيم النظري. لا تنشئ ملفات Placeholder لمزايا مستقبلية. بعد كل Phase راجع عدد الملفات والمجلدات والتبعيات، وإذا كان النمو أسرع من القيمة الوظيفية فقم بالتبسيط قبل إعلان PASS.

المحركات مفتوحة المصدر مثل STT/TTS هي **Adapters قابلة للاستبدال وليست قلب المعمارية**. يجب أن يستفيد التطبيق من قدراتها الحقيقية عبر `Capability Manifest`، وأن يعرض الـSidebar فقط الإعدادات التي يدعمها المحرك/النموذج المختار فعلًا. لا تفترض قدرة أو ترخيصًا غير موثق.

افصل دائمًا بين:

**Voice Profile = من يتحدث**

و:

**Voice Direction = كيف يؤدي الكلام**

والـNarration Director هو المسؤول عن توجيهات الأداء المحايدة عن المحرك، بينما كل Adapter يترجم فقط ما يستطيع محركه تنفيذه.

حافظ أيضًا على المبدأ المركزي للمشروع:

> **Many Sources → One Understanding → Many Stories → Many Formats → Many Languages → Many Performances**

أي أن المصدر يُفهم مرة واحدة ويُبنى منه `Knowledge Model` قابل للتتبع والتحديث، ثم تتفرع منه المخرجات. لا تعِد تحليل المصدر كاملًا لكل Audio أو Booklet أو Audience جديد.

ابدأ الآن حصريًا بـ:

**Phase 0 — Reconnaissance and Baseline**

اقرأ الوثيقتين كاملتين، افحص المستودع والبيئة، نفذ متطلبات Phase 0، شغّل الاختبارات المطلوبة، وقدم `VOXA STUDIO PHASE CHECKPOINT`.

لا تنتقل إلى Phase 1 إلا بعد أن تكون Phase 0 بحالة **PASS**.

من هذه اللحظة أنت **Principal Implementation Engineer** للمشروع، والوثيقتان هما السلطة الهندسية التي يجب أن يطابقها التنفيذ.
