# AgentCraft — Universal Project Delivery & Visual Fidelity Standard
## المعيار الموحد لإدارة المشاريع والتصميم والتطوير والمراجعة عبر GitHub

**Document ID:** `AGENTCRAFT-UNIVERSAL-WORKFLOW-STD-001`  
**Version:** `1.0`  
**Status:** معيار عمل معتمد للاستخدام في المشاريع الحالية والقادمة، ويُخصَّص لكل مشروع دون إلغاء قراراته السابقة.  
**Primary documentation repository:** `https://github.com/mayakilzy/repo-info`  
**Audience:** مالك المشروع، مشرف التصميم والهندسة، وكلاء البرمجة (GLM / Codex / غيرهم)، المراجعون والمساهمون.

## 1. لماذا اعتمدنا هذا المعيار؟

بدأت التجربة من مشكلة متكررة: نصمم واجهة بصرياً ونوافق على صورتها، ثم نرسل الصورة إلى وكيل برمجي مع تعليمات عامة؛ فينشئ نسخة «مستوحاة» بدلاً من التصميم نفسه. نحاول إصلاحها بنصوص إضافية ولقطات شاشة متنقلة بين الجلسات، فتكثر الاختلافات، وتضيع الأدلة، ويصعب معرفة هل نجح التطوير أم لا.

**الحل المعتمد مزدوج:**

1. **GitHub مركز موحّد للمصدر والأدلة:** الكود في مستودع التطبيق، وقرارات التصميم والوثائق ولقطات التحقق في مساحة المشروع داخل `repo-info`.
2. **Visual-first, source-driven implementation:** نعتمد الصور الأصلية، ثم نصنع منها مرجعاً تنفيذياً **HTML/CSS/SVG/Assets** يُفتح في المتصفح ويُراجع، ثم يستورده المطور إلى التطبيق الحقيقي بوصفه عقداً بصرياً ملزماً، مع الحفاظ على وظائف التطبيق.

**المبدأ الأعلى:** نطلب من المطور تنفيذ ما تم اعتماده، لا تخيل تصميم بديل. **النجاح الوظيفي لا يساوي النجاح البصري، والنجاح البصري لا يبرر وظيفة وهمية.**

## 2. نطاق التطبيق والأدوار

تُطبّق هذه السياسة على **كل مشروع حالي أو قادم**؛ قد تختلف التقنيات (React / Next.js / Vue / تطبيق هاتف / لوحة تحكم) لكنها لا تُغيّر قواعد التسليم والتحقق. ولا يحق لهذا المعيار وحده نقض سياسة أمن أو خصوصية أو ترخيص أعلى منه.

| الدور | المسؤولية | ما لا يحق له القيام به منفرداً |
|---|---|---|
| **مالك المشروع (Owner)** | اعتماد الرؤية والتصميم والنطاق والقبول النهائي والتقدم إلى المرحلة التالية | — |
| **مشرف التصميم والهندسة (ChatGPT)** | صياغة المواصفات، تجهيز/مراجعة مصادر HTML/CSS، التدقيق، مقارنة الأدلة، صياغة المهام، التوصية بالقبول | الادعاء بتشغيل ما لم يُشغّل أو اعتماد تعديل جوهري نيابة عن المالك |
| **وكيل التنفيذ (GLM أو أي مطور)** | تطوير التطبيق والاختبارات والدمج والتصوير والتقرير والرفع | إعادة تصميم المرجع، اختلاق بيانات، أو تخطي بوابات القبول |
| **وكيل الاسترداد/النشر (Codex أو بيئة مخوّلة)** | إصلاح تعارضات Git، تطبيق رقع موثقة، PRs، المساعدة في النشر والتحقق | استبدال المطور الأساسي أو تعديل `main` قسراً |

الأدوار **وظائف قابلة لإعادة التوزيع** وليست تقييداً لأسماء أدوات بعينها.

## 3. إنشاء مساحة مشروع جديدة داخل repo-info

قبل أول مهمة برمجية أو بصرية لمشروع جديد:

1. تثبيت **اسم المشروع الرسمي** واسم الـ slug، ومكان مستودع الكود التنفيذي.
2. فحص ما هو موجود بالفعل في `repo-info` والمستودع التنفيذي لتجنب إنشاء هياكل موازية أو نقل ملفات دون داعٍ.
3. إنشاء مجلد مستقل للمشروع تحت `repo-info/<PROJECT_SLUG>/` بعد الموافقة وتحديد ما إذا كانت الوثائق كلها صالحة للنشر في هذا المستودع.
4. إنشاء ملف `START_HERE.md` يحوي الروابط، الرؤية، المرحلة، المرجع المعتمد، خريطة المهام، وقرارات المالك.
5. حفظ نسخ الوثائق مع أرقام الإصدارات ومرجع SHA الدقيق؛ المستندات المعتمدة لا تُستبدل بصمت.
6. إن كانت المعلومات سرية أو تحتوي بيانات شخصية أو حقوقاً خاصة، **لا تنشرها في مستودع عام**؛ استخدم مستودعاً خاصاً مخوّلاً أو وسيلة مناسبة مع وضع رابط فهرسة غير حساس فقط.

### 3.1 شجرة مرجعية قابلة للتخصيص

```text
repo-info/
└── <PROJECT_SLUG>/
    ├── START_HERE.md
    ├── PROJECT_CONTEXT/
    │   ├── VISION_AND_SCOPE.md
    │   ├── ARCHITECTURE_AND_API_MAP.md
    │   ├── CURRENT_STATE_AND_HANDOFF.md
    │   └── DECISION_REGISTER.md
    ├── UI_UX_DESIGN/
    │   ├── APPROVED_VISUAL_ASSETS/
    │   ├── DESIGN_SYSTEM/
    │   ├── PAGE_TO_VISUAL_MAPPING.md
    │   ├── DESIGN_LOCK_AND_EXCEPTIONS.md
    │   └── IMPLEMENTATION_READY/
    │       ├── SHARED_COMPONENTS/
    │       ├── PAGE_01_<NAME>/
    │       │   ├── index.html
    │       │   ├── styles.css
    │       │   ├── script.js             # إذا احتاج المرجع لسلوك توضيحي
    │       │   ├── assets/
    │       │   ├── README.md
    │       │   └── REFERENCE_MANIFEST.json
    │       └── PAGE_02_<NAME>/
    ├── IMPLEMENTATION_REVIEWS/
    │   └── <MISSION_ID>/
    │       ├── REPORT.md
    │       ├── visual_comparison.md
    │       ├── playwright_results.json
    │       ├── screenshots/

```

هذه الشجرة **اقتراح قياسي** لا يُفرض حرفياً على مشروع منظّم بالفعل. يمكن اعتماد مسار `IMPLEMENTATION_READY/` مباشرة تحت مجلد المشروع للتوافق مع إرث موجود، بشرط تدوين المسار المعتمد في `START_HERE.md` وعدم إنشاء نسختين متنافستين.

## 4. حدود المستودعين (Repository Boundaries)

**مستودع التطبيق:** شيفرة الإنتاج، مكونات UI، الاختبارات، الملفات البرمجية، بنية التشغيل، migrations، حزم الاعتمادات، ضبط CI.

**مستودع الوثائق `repo-info`:** الصور والمرجع البصري المعتمد، مواصفات الصفحات، HTML/CSS المصدر **المرجعي غير التشغيلي للإنتاج**، القرارات، screenshots، نتائج Playwright، تقارير الاختلافات، ملفات التسليم والاسترداد عند الضرورة.

لا يُحفظ كود الإنتاج في `repo-info` بديلاً عن نشره إلى مستودع التطبيق. ولا يُعد وجود حزمة محلية أو commit محلي دليلاً على أنها وصلت إلى GitHub. **نجاح الدفع يُثبت فقط بفحص المستودع البعيد وSHA.**

### 4.1 وثيقة البداية الإلزامية

يحتوي `START_HERE.md` في كل مشروع على: اسم المشروع، مستودع الكود، مستودع وثائق المشروع، الفرع الرسمي، أحدث SHAs معتمدة، قائمة الصفحات وحالاتها، الأصول البصرية وتراخيصها، مالك القرار، المهام المسموح بها والممنوعة، آخر تقرير نجاح/فشل، وكيفية استئناف جلسة جديدة.

## 5. دورة التصور والتصميم واعتماد الصورة

1. **اكتشاف المتطلبات:** ما الذي يفعله المنتج؟ لمن؟ وما القيود التقنية والوظيفية الحقيقية؟
2. **خريطة صفحات وتجارب:** حالات المستخدم، التنقل، العناصر المشتركة، API المتوقع، حالات التحميل/الخطأ/الفراغ/النجاح.
3. **تصميم بصري:** صورة أو أكثر لكل صفحة: Desktop ثم Mobile/Tablet وEN/AR عند انطباقها.
4. **اعتماد المالك:** تعيين مرجع أساسي ومرجع داعم وأصول `APPROVED` و`DIRECTION` و`SUPPORTING` و`FUTURE`. لا تصبح الصورة معتمدة بمجرد وجودها في الحزمة.
5. **قفل التصميم (Design Lock):** ألوان، خطوط، شبكة، هوامش، تسلسل بصري، حركة، Responsive وRTL، وحالات العناصر.
6. **مطابقة الواقع الفني:** استبعاد أو تعطيل أي أزرار أو بيانات لا يدعمها Backend/الصلاحيات الحالية، مع المحافظة على التكوين البصري قدر الإمكان. أي اختلاف مفروض يوثق كاستثناء يوافق عليه المالك.

**ممنوع:** إخراج بيانات بحث أو سجلات أو أعضاء أو نسب ثقة أو مؤشرات أعمال مختلقة وكأنها حقائق. يجوز استخدام بيانات عروض اصطناعية موسومة بوضوح في معاينة التصميم أو قاعدة اختبار معزولة، ولا تُعرض على أنها نتائج حية.

## 6. التحول الحاسم: من الصور إلى HTML/CSS مرجعي جاهز للتنفيذ

بعد اعتماد الصورة وقبل تكليف وكيل التطوير بإعادة إنتاج الواجهة:

1. يُنشئ مشرف التصميم **حزمة مصدرية لكل صفحة**: `index.html` و`styles.css` و`assets/` و`README.md`، مع `script.js` إذا احتجنا لتجربة حالات تفاعلية.
2. يعتمد على **الأصل الفني نفسه** بقدر الإمكان؛ لا يستبدل العمل المصور المعتمد بأيقونة عامة، ولا يعالج الصور بطريقة تفسد تفاصيلها. يراعى الترخيص والملكية.
3. تكون العناصر الطباعية والتخطيطية وواجهة الاستخدام الفعلية **DOM/CSS حقيقيين**؛ لا تُستعمل صورة الشاشة كلها بوصفها واجهة ثابتة بديلة.
4. يعكس المرجع نظام التصميم بدقة: الخطوط، المقاسات، الظلال، الألوان، الأيقونات، النسب، حالات Focus وHover، RTL وResponsive.
5. المرجع **قابل للعرض محلياً دون اعتماد على Backend** ويستخدم بيانات عرض موصوفة بوضوح؛ ليس منتجاً نهائياً.
6. يُشغَّل في متصفح حقيقي وتُلتقط صورة بنفس أبعاد الصورة المعتمدة. تُسجل اختلافات المرجع ويُصحح ما هو جوهري **قبل إرسال المهمة إلى المطور**.
7. يُكتب `REFERENCE_MANIFEST.json` أو قسم في README يحوي: الصورة المعتمدة وSHA، ملف المصدر، حجم العرض، الخطوط/التراخيص، قائمة الأصول، حالة المطابقة، الاستثناءات المصرح بها.
8. يُرفع المصدر إلى `repo-info/<PROJECT>/UI_UX_DESIGN/IMPLEMENTATION_READY/PAGE_XX/` أو المسار المعتمد المكافئ، مع نسخة مُرقمة قابلة للاسترجاع.

**ملاحظة صدق:** عندما توجد صورة معتمدة فقط وليس HTML سابق، **يجب إنشاء HTML الآن**. لا يجوز الادعاء بأن كود الصورة الأصلي موجود إذا لم يكن قد أُنتج.

### 6.1 سلسلة المطابقة الإلزامية

```text
Approved Image  →  Standalone HTML/CSS  →  Real App (React / other UI)
       Gate A                  Gate B                   Gate C
```

- **Gate A — Design approval:** صاحب المشروع اعتمد الصورة والمستثنيات الوظيفية.
- **Gate B — Reference fidelity:** المرجع HTML نفسه قريب بصرياً من الصورة، مع توثيق أي انحراف متعمد.
- **Gate C — App fidelity:** التطبيق الحقيقي يطابق مرجع HTML ويؤدي الوظائف الحقيقية.

لا معنى لمطالبة المطور بنسخ مرجع لم يُتحقق بصرياً منه أولاً.

## 7. مهمة المطور: استيراد المصدر بدلاً من إعادة التصميم

ينبغي أن يتلقى وكيل التطوير **المسار الدقيق** إلى الحزمة في `repo-info`، ونصوص القبول الواضحة:

1. اقرأ `START_HERE.md`، المواصفات، `README.md` الخاص بالمرجع، وصورة التصميم المصدّقة.
2. افحص SHA وحجم الأرشيف وسلامة ZIP؛ شغّل صفحة HTML مستقلة وصورها أولاً.
3. تأكد من تطابق المرجع HTML مع الصورة المعتمدة؛ إن اختلفا اختلافاً جوهرياً، **توقف وصعّد سبب الاختلاف** إلى المشرف.
4. حوّل HTML/CSS إلى مكونات التطبيق مع الاحتفاظ بالتوزيع البصري والقيم التصميمة والنصوص والأصول، **دون تضمين الصفحة في iframe** ودون تكرار shell التطبيق أو تعطيل routing/state.
5. اربط الأزرار بالحالات وواجهات API والحقوق والبيانات الحقيقية؛ لا تحفظ سكربت العرض التوضيحي بديلاً عن الوظيفة الحقيقية.
6. استخدم مكونات مشتركة (Header/Sidebar/Tokens) عبر الصفحات، لكن **لا تغيّر تصميمها المتفق عليه** دون اعتماد عابر للصفحات.
7. نفّذ الترجمة العربية/الإنجليزية الصحيحة وRTL وResponsive وتسهيلات الوصول.
8. اختبر تحميل الصفحة والمحتوى الحقيقي والأخطاء والفراغ، وتحقق من أن التغييرات لم تُعطّل الصفحات السابقة.
9. صوّر واجهة التطبيق من المتصفح وقارنها بالمرجع HTML ثم بالصورة الأصلية، وأصلح كل فرق مادي.
10. لا تنتقل إلى الصفحة التالية دون تفويض قبول صريح.

**الاستثناءات:** عندما يكون العنصر الظاهر في الصورة غير مدعوم وظيفياً، يُصنّف كـ `FUNCTIONAL_GAP` ويُقترح تكيف يحافظ على التوازن البصري؛ لا يُصنع زر فعّال وهمي.

## 8. دورة الصفحة الواحدة — Page Acceptance Loop

**لكل صفحة** (وليس فقط في نهاية المشروع):

| خطوة | مخرج مطلوب |
|---|---|
| 01 — Design Lock | صورة معتمدة + خريطة عناصر + قرار صاحب المشروع |
| 02 — Source Build | HTML/CSS/SVG/Assets + README |
| 03 — Source Screenshot | صور Desktop/Mobile وRTL كما يلزم |
| 04 — Source Comparison | approved-versus-HTML diff وتقرير الفروقات |
| 05 — Developer Import | كود التطبيق + ربط API الحقيقي |
| 06 — Browser Verification | Playwright assertions والتقاط actual screenshot |
| 07 — App Comparison | approved / HTML / app بزاوية العرض نفسها |
| 08 — Corrections | إصلاح الفروقات في الكود أو تصعيد مشاكل المرجع |
| 09 — Dual Repo Delivery | SHAs منشورة + تقرير + صور |
| 10 — Owner Verdict | `ACCEPTED` أو `CONDITIONAL` أو `REJECTED` مع المتبقي |

**قاعدة التصعيد:** على المطور الإبلاغ عن الصفحة والعنصر والفروق الدقيقة وسبب العائق، وليس تقديم تصميم بديل يسهل تنفيذه. يجهز المشرف HTML/CSS/SVG تفصيلياً لذلك الجزء عند الحاجة.

## 9. بوابات الجودة الأربع

### A — Visual Fidelity
- متسق مع التصميم المعتمد من حيث شبكة الصفحة، التناسب، المسافات، الخطوط، الصور، الألوان، الأيقونات، كثافة المعلومات، الهرمية وحالات التفاعل.
- तुलना الصور بالحجم/الـ viewport نفسه، مع مقارنة جانبية ويمكن استخدام overlays/diff حيث تفيد.
- لا يُعتمد رقم تشابه اعتباطي ولا حكم VLM إيجابي دون رؤية نتيجة التطبيق.
- اختلافات المحتوى الواقعي عن mockup مسموحة **إذا لم تُستخدم ذريعة لحذف بنية التصميم**؛ اختبر محتوى مُعبأً ببيانات تطوير واضحة وحالة فارغة صادقة.

### B — Functional Fidelity
- توافق عقود API، صلاحية التفاعل، تحميل/نجاح/فشل/حدود/عدم اتصال، عدم إخفاء أخطاء API كقوائم فارغة أو نجاحات وهمية، احترام الصلاحيات.
- اختبارات وحدات ومكونات وتكامل، typecheck/lint/build وفحوص Backend المتعلقة بالتغيير.

### C — Responsive, Accessibility & Language
- Desktop, Tablet, Mobile؛ العربية والإنجليزية عند اعتمادها؛ دعم اتجاه RTL؛ focus/keyboard/contrast/labels؛ لا overflow أو نقص محتوى؛ احترام تفضيلات تقليل الحركة إن استُخدمت مؤثرات.

### D — Evidence & Delivery Integrity
- لقطة الشاشة تحمل اسم الصفحة والحالة الصحيحة ويُتحقق من عناصرها **قبل التصوير**.
- سجلات الاختبارات صادقة؛ الادعاءات مبنية على أمر جرى تشغيله في هذه المهمة ونتيجته.
- الكود منشور في مستودع التطبيق، والأدلة منشورة في `repo-info`، مع تحقق مباشر من SHAs البعيدة.

**نتيجة الصفحة:** PASS فقط عند نجاح البوابات الأربع حسب نطاقها؛ وإلا `CONDITIONAL` أو `FAIL` أو `BLOCKED` بأسباب واضحة.

## 10. نظام أدلة المراجعة — لا مزيد من تنزيل ورفع الصور يدوياً

بعد كل مهمة:

- يضع المطور صور PNG/WebP مضغوطة بطريقة تحافظ على وضوح النص داخل `IMPLEMENTATION_REVIEWS/<MISSION_ID>/screenshots/` **بأسماء واضحة**.
- يرفع `REPORT.md` و`visual_comparison.md` و`playwright_results.json`، وسجلات محدودة عند الحاجة.
- يضمّن روابط الصور نفسها وروابط المقارنات وروابط commits، بدلاً من الاكتفاء بملف ZIP كبير.
- يراجع مشرف التصميم النتائج **مباشرة من GitHub** عبر التكامل المتصل إذا أمكن؛ إن كان التكامل لا يعرض ملف صورة ثنائياً، يذكر القيد ويستخدم وسيلة آمنة متاحة، ولا يدّعي فحص صورة لم يرها.
- لا حاجة لأن يحمل المالك الصور ويعيد رفعها إلى كل محادثة ما دام المستودع يتيح الوصول إليها.

### 10.1 تسلسل دليل Playwright

قبل كل screenshot يؤكد المتصفح آلياً:
1. Route/heading الصحيح.
2. المكون المطلوب ظاهر وليس Hero من صفحة أخرى.
3. الحالة الصحيحة (populated/empty/error/loading) مؤكدة بعنصر أو response.
4. الصفحة انتهت من تحميل الخطوط والأصول عند قياس الشكل.
5. لا توجد أخطاء console غير معالجة ذات صلة.

يُحظر تسمية صورة Home باسم Workspace أو اعتبار وجود عنوان «Replay» دليلاً على أن إعادة التشغيل الزمنية نجحت بالفعل.

## 12. Git Workflow والاسترداد الآمن

### 12.1 قبل العمل
- `git fetch` والتحقق من origin/main أو الفرع المعتمد، وفحص `git status`.
- لا تبدأ من SHA قديم دون تفقد أحدث تغييرات الآخرين.
- يفضل فرع مهمة واضح، ثم PR إذا كانت سياسة المشروع تقتضي ذلك. لا يُفرض الدفع المباشر إلى `main`.

### 12.2 بعد العمل
- Commit تغييرات الكود في مستودعه، والتقرير/الأدلة في مستودع الوثائق.
- تحقّق من نشر كل منهما فعلياً عبر `git fetch` ومقارنة remote SHA أو API.
- إذا نجح أحد المستودعين وفشل الآخر: حالة التسليم **PARTIAL** لا **COMPLETE**.

### 12.3 عند تعذر الدفع
- احتفظ بالالتزامات المحلية وبنسخة قابلة للاسترداد من patch باستخدام `git format-patch` أو حزمة مناسبة، مع Base SHA ووصف ترتيب تطبيقها.
- لا تُخزن أي رمز اتصال داخل الرقعة أو اللوج أو المستودع العام.
- تطبّق الرقع في بيئة مُخوّلة على **فرع استرداد** من أحدث remote، مع فحص الأسرار والتعارضات والاختبارات، ثم PR.
- **ممنوع:** `git reset --hard` عشوائياً، `git push --force`، تغيير تاريخ `main`، أو `git am` على أساس غير مفحوص.
- لا تنشئ patch مرجعياً متضمناً نسخة من ذاته داخل الالتزام؛ احتفظ بالرقعة خارج الملفات التي تمثّلها.

## 13. أمن المستندات والملفات والأصول

- افحص `repo-info` بحسب **صلاحية الوصول الفعلية** قبل نشر ملفات. لا تضع PATs أو .env أو رموز وصول أو مفاتيح API أو معلومات اتصال حساسة ضمن مشروع عام.
- راجع screenshots لمنع كشف معلومات شخصية أو بيانات عملاء أو مفاتيح أو عناوين حساسة.
- لا ترفع logs كبيرة أو raw dumps إلا عند الحاجة وبعد تنقيحها.
- لا يُعد `chmod 600` وحده مبرراً للاحتفاظ غير المحدود بالرموز؛ اعتمد مبدأ أقل صلاحية، مدة محدودة، وتدوير/سحب الرمز عند انتهاء الحاجة.
- تحقّق من تراخيص الخطوط والصور والأيقونات والمكتبات؛ لا توزّع ملفات خطوط غير ضرورية ضمن التسليمات.
- الأدلة العلمية والشخصية في النظام الحقيقي لا تُنشر إلى repo-info لأغراض المراجعة.

## 15. مراحل إطلاق المشروع كاملاً

**Phase 0 — Foundation:** مستودعات، README، Vision، معمارية، تعريف الأدوار، صلاحيات.

**Phase 1 — Functional Mapping:** قدرات backend، خريطة الصفحات، عقود API، حالات المستخدم.

**Phase 2 — Visual Design:** صور، قرارات اعتماد، Design System، Responsive/RTL، Design Lock.

**Phase 3 — Executable Visual References:** HTML/CSS/SVG لكل صفحة، مراجعة متصفح وتطابق مع الصور قبل البرمجة.

**Phase 4 — Application Integration:** تنفيذ React/التقنية الفعلية، ربط وظائف، اختبارات، مقارنة صور، قبول صفحة بصفحة.

**Phase 5 — Cross-Page Integration:** اتساق المكونات والتنقل، حالات التحميل والفراغ والخطأ، تجربة كاملة، اختبارات تراجع.

**Phase 6 — Deployment Readiness:** تدقيق أسرار وأمان، بناء Docker/بيئة مناسبة، إعداد التشغيل والمراقبة والمستندات، ثم قرار إطلاق مستقل من المالك.

لا تقفز من نجاح صفحة إلى إعلان انتهاء تطوير التطبيق كله.
